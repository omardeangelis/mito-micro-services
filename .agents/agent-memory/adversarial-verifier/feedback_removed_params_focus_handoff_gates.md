- **"The parser ignores the removed URL params" claims: find the component that WRITES the param and the builder that READS it.** Here the plan named `filter_by` + UI labels ("Stato"), but the advanced filter writes `filter=<column_name>:<op>:<value>` (`PopoverFilter.tsx` `searchParams.append("filter", ...)`) and `createSQLFilter` interpolates ANY name into SQL without consulting the map, so dropping a key from the map drops nothing. A test written to the plan's wording passes vacuously, and while the join still exists even the browser check passes: the break shows only after the query loses the join.
  **Why:** map keys (labels) and URL names (column names) differ. **How to apply:** any AC of the form "saved link with removed filter opens ignoring it".
- **When a task deletes a control, grep surviving components for its data-attribute/selector.** `CustomerCreateContact` hands focus to `STATE_TRIGGER_SELECTOR` (the state selector of the card the task deletes), so focus lands on `body` after "Crea contatto". Also grep comments that name deleted symbols: a "grep returns nothing" validation fails on stale comments in files outside the task's `location`.
- **A gate that demands "adversarial-review SHIP of X" needs a REPORT.md round with that verdict.** Check `REPORT.md` frontmatter and the round headings; "fixed and verified by the owner" is not a SHIP round, and a review of the new branch does not cover an earlier PR already on dev.
- **A release step that runs `db:migrate:prod` applies every pending migration in one transaction.** List them with `git diff origin/main..HEAD --stat -- src/server/db/migrations` (here three: cron_run, the index drop with `SET LOCAL lock_timeout`, the new one). `SET LOCAL` and the ACCESS EXCLUSIVE lock last until COMMIT and cover the later migrations' statements.
- **Gate scripts that decide stop/go need their own test.** The precedent `cleanupPreview.db.test.ts` tests the preview script; a new extraction script without one makes "0 and 0" vacuous.
- **A server-side discard does not change what CLIENT components read from the same URL.** Second pass on PR6: the plan said "with the discard there is no ghost row in the advanced-filter popover", but `PopoverFilter.tsx` reads `window.location` itself and maps an unknown column to `?? "Nato il"`, which is not a key, so `filterMap.get(name)!.columnType` throws; the popover's ErrorBoundary shows "Something went wrong." (its Retry does `() => this.props.handleError`, never calls it). Probe: copy the repo to the scratchpad, symlink node_modules, render the real component with the trimmed map and `window.history.pushState(null, "", "/?filter=state:eq:chiamare")`, click the trigger, print `document.body.textContent`. Same for `filter_by`: `useGetMultipleUrlParamsValues`/`generateFilter` adds any unknown key, so a dismissible chip for the removed filter stays.
  **How to apply:** for each removed param, grep every reader (`useSearchParams`, `window.location`, `searchParams.getAll`), not only the server page.
- **Run the plan's literal param string through the real parser before accepting "the test uses the real parameters".** `filter_by` is `[status]=chiamare` (URL-encoded, comma-separated, `-` joins values); the plan's `filter_by=status-chiamare` gives `Object.fromEntries(map) = {}` through `getUrlParmsWithMultipleValue`, so a test with that literal passes with no discard code at all.
- **After a rewrite moves WHEN a gate closes, read the gate table cells, not only the task text.** G4a/G4b rows still said "Prima del deploy" and G4b's "G4a chiuso" while T6.7 applied the index migration after the deploy: a circular precondition. Also compare per-task `complexity` in the wave section with the task blocks (T6.3 `low` vs `medium`).
- **Data-modifying CTE in one statement (PGlite 0.2.17 probe):** `UPDATE ... RETURNING` yields only NEW values, so a log with `from_operator_id` needs a read CTE (`target`) joined into the UPDATE and the INSERT; the single statement is feasible and idempotent on rerun.
