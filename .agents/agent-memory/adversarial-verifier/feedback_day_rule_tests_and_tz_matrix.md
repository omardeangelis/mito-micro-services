---
name: day-rule-tests-and-tz-matrix
description: Tests for a calendar-day rule that only use midnight inputs cannot tell it from an instant compare; and check that a TZ=... matrix really changes the worker zone
metadata:
  type: feedback
---

A rule like "reject a deadline whose Rome day is today or earlier" was tested only with deadlines at Rome midnight (what a date picker sends). The mutant `deadline.getTime() <= Date.now()` (instant compare) passed 23/23 service tests and 11/11 unit tests, because at midnight the two rules agree. The inputs that separate them are a later-today instant (17:00 Rome) and the last millisecond of today (`tomorrowMidnight - 1`), on a summer day, a winter day and both DST change days. A probe with those 7 cases passed on the real code and killed the instant mutant 5 times.

**Why:** the rule exists for callers other than the picker (direct API calls with any instant), so tests built on picker values prove nothing about it. A UTC-day mutant (the one the charter named) was killed, which hides this gap if you stop there.

**How to apply:** for any day-bucket rule, run three mutants: UTC day, instant compare, `start + 24h` (the last also survives when no test sits on a DST day). Add boundary cases on both sides of the midnight (`-1 ms` rejected, `+0` accepted), not only the accepted side.

**TZ matrix:** `vitest.config.ts` here sets `env: { TZ: "UTC" }`, yet a shell `TZ=Pacific/Auckland pnpm exec vitest run` still ran the worker in Auckland (a probe test printing `Intl.DateTimeFormat().resolvedOptions().timeZone` and `getTimezoneOffset()` showed `UTC` in `process.env.TZ` but `Pacific/Auckland` and -720 in Intl). Do the probe once before trusting a TZ matrix; do not infer from the config. For an independent oracle of a Rome-day rule use PGlite: `(x::timestamptz at time zone 'Europe/Rome')::date` through `testDb.execute(sql...)`.

**Second pass on the same rule (callback-from-tomorrow, after the instant mutant was fixed):** the author added later-today and `end - 1` cases on 4 days (summer, winter, 23h, 25h) and the UTC-both, instant, `start + 24h`, local-day and message mutants all died. Two mutants survived every test in 4 TZs: Rome day of the deadline vs UTC day of `now` (`romeDay(d) <= now.toISOString().slice(0,10)`), and the same with the process-local day of `now`. Cause: every fake `now` was 10:00Z, where the UTC day equals the Rome day. The distinguishing window is `now` in [22:00Z, 24:00Z) summer / [23:00Z, 24:00Z) winter (00:00-02:00 in Rome, which is where the nightly cron runs). A 6-case probe (summer, winter, both DST days, and the two days after them, `now` at 00:30 Rome; deadline = start rejected, `end - 1` rejected, `end` accepted) passed on real code and killed both survivors in unit and service form.

**How to apply:** for a day rule, mutate the `now` side separately from the `deadline` side (UTC for `now` only, local for `now` only). Grep the test's fake nows: if none sits just after Rome midnight, the `now` side is untested. A unit test for the sibling function (`isPastDay`) having the straddle `now` does not cover `isDueOrOverdue`.

**Config TZ is not effective:** with no shell TZ the worker's Intl zone was the machine zone (Europe/Rome here), not the `TZ: "UTC"` of `vitest.config.ts`; so a process-local-day mutant passes on the developer's machine and dies only in CI or with a shell `TZ=`. Always run the matrix with explicit TZ values (UTC, America/Los_Angeles, Asia/Tokyo) and note the default is the machine zone.

**Third pass (after the 00:30-Rome cases were added):** UTC-now, local-now and UTC-both mutants all died in UTC/LA/Tokyo; local-day mutants survive only under Europe/Rome, where they are equivalent. One residue: a service mutant that shifts `now` forward by 2h (`new Date(Date.now()+7200000)`) was killed by one real-clock test only because the run happened at 23:43 Rome; at midday it survives. A real-clock test that kills a mutant is time-of-day luck: re-run the mutant under a fake clock, and ask for a `now` just before Rome midnight (23:30 Rome, deadline `end` accepted, `end - 1` refused).

**Fourth pass (UI side: list highlight, picker, SSR on a UTC server):** the rule helpers were Rome-pinned and right, but the DISPLAY used `getDate()/getMonth()` (process zone). Tests expected `formatDateAsDMY(sameDate)` (the formatter under test), so they pass in every zone and prove nothing about the day shown. Server Components bake the UTC day into the RSC payload (never re-formatted in the browser); client components SSR in UTC then hydrate in Rome (text mismatch). Checks that found it: (1) `renderToString` of the Server Component under `TZ=UTC` vs `TZ=Europe/Rome` and diff the text; (2) two vitest processes (server mode writes html, client mode `hydrateRoot`s it under another TZ; `process.env.TZ` cannot be switched inside a worker) and read `onRecoverableError` + console.error; the control (same TZ both) must be clean; (3) a `now` prop from a Server Component is NOT the mismatch (Date goes through Flight as `$D`), the formatter is. A local dev server on a Rome machine hides all of this: check `ps eww -p <pid>` for TZ and the machine zone.
**Picker differential:** spy the helper via `vi.mock` wrapping `vi.importActual` to record the instants DayPicker hands to `disabled`, then compare each flag with an independent `Intl en-CA Europe/Rome` oracle at 10 nows (00:30 Rome summer/winter, both DST days at 00:30 and 23:30, the day after) in 5 zones. For Rome browsers midnight cells make "instant compare" equivalent to the Rome-day rule, so those mutants survive legitimately; they differ only in far-east zones. A test asserting local day numbers (`dayButton(16)` enabled) fails in Tokyo/Auckland/Kiritimati while the instant-compare mutant PASSES there.

**Fifth pass (Rome date formatter + windows test moved into `timeZoneTests`):** moving a `*.db.test.ts` into the list drops it from the `unit` project (`exclude`) and runs it in `utc` and `rome` forks only: confirm with `--project unit <dir>`. In those forks TZ IS effective: a calendar-day mutant (`d.setDate(d.getDate() - n)`) survived in `utc` and died in `rome`, while `setUTCDate` and `now - span - span` are equivalent mutants. A format fixture of 23:30Z winter + 22:30Z summer kills UTC, process-zone, `Etc/GMT-1` and New York, but `Etc/GMT-2` and `Europe/Athens` survive (both give the same date on those two instants): add a winter instant in [22:00Z,23:00Z). `comparison.end == reference.start` by construction, so swapping those two slots in the card is an equivalent mutant.
